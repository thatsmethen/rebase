# Windows parity

The behavior comparison baseline is the macOS **0.21.1** application, including its bundled example beat. The visual target is the [Cubase Pro 15.0.30 Windows interface](windows-ui-fidelity.md). The [Windows development preview](https://github.com/thatsmethen/rebase/releases/tag/v0.21.1-windows-preview.8) includes the native WPF package, compact/normal track rows, adjustable panels, shared waveforms, musical ruler, volume/pan automation editor, reviewed partial CPR import, eight shared source-audio modes and explicit device-rate adaptation. The captured selector/header defects have been corrected; exact reference fidelity remains open. The public repository, research export, and existing Mac downloads remain available.

## Shared implementation

Windows and macOS use the same authored Swift project/CPR models and C DSP sources. The portable Swift target selects those source files directly; it does not translate the engine into another language. PCM ownership, file decoding, device output, filesystem operations, and presentation are explicit boundaries.

The shared renderer extracts ordinary clip preparation and Float32 accumulation into `PCMRenderer`. macOS now calls that implementation through its AVFoundation decoder. The portable WAV adapter reads bounded mono/stereo PCM16/24/32 and float32/64 RIFF files. It does not support compressed, extensible, big-endian, or RF64 inputs yet. CPR source preparation, placed/overlap streams and their reconstructed conversion/ring/callback stages now share portable PCM ownership; macOS copies those same blocks into AVFoundation buffers. Device output remains a separate host boundary.

Document commands, selection, snapping and bounded undo/redo now share `ProjectEditing` and `ProjectEditHistory`; the Mac session uses those same sources. Windows presentation and file operations remain separate integration work.

The x64 lane explicitly qualifies the floating-point environment before enabling six previously arm64-only kernels. Independent numerical controls and altered-environment rejection tests exercise the extension. Passing these controls demonstrates reconstructed-code portability within the tested domain; it is not evidence from a proprietary Windows reference executable.

### Device-rate adaptation

The native adapter prepares the whole immutable snapshot for differing source/device rates with pinned public SoXR 0.1.3 VHQ, linear-phase conversion before playback. Source and endpoint must be Float32 stereo at 8–192 kHz. Equal-rate samples remain bit-exact; project renders and their existing locks remain unchanged. The ABI still reports and seeks in source frames, with separate endpoint-frame diagnostics. Pause captures the frozen native position before source audition reconstructs and revalidates its input. Seek reads the actual mapped position, including rounded endpoint EOF; delayed status polls cannot overwrite a newer transport action. Source and converted snapshots each have a 32-million-frame limit; conversion rejects empty results, unsupported output formats, invalid floating-point environments and incomplete drain. See the [native contract](../../Application/Windows/NativeAudio/README.md) for the profile and quantization rules.

This is an authored device policy, not the reconstructed CPR Mode 2 policy or evidence of native reference playback parity. The retained REA [processed-stream study](../../research/evidence/cubase-static/cpr-audio-events-001/processed-stream-rate/finding.json), `CPR-PROCESSED-STREAM-RATE-001` / `PSR3`, observes input-rate forwarding for the inspected Float32 wrappers (`ev_b5755391f10c4028bd5c9bdcfb38c62277e90a18bfac8841e2c4d24a3c047012`). Its grouped-stream conversion boundary is distinct from project and device clocks. The [prepared-stream study](../../research/evidence/cubase-static/cpr-audio-events-001/prepared-stream-rate/finding.json), `PREP-RATE-1`, likewise does not establish project-rate conformance. Those static findings are reused; no new reference execution or sample-equivalence claim follows from this adapter.

Windows Debug/Release conversion and lifecycle controls passed, and the package includes the app-local SoXR DLL with its complete public source and notices. The 268 host controls cover converted metadata, source provenance, immediate pause/resume, quantized EOF, stale polls and pre-native array validation. These use authored adapters; hardware playback remains unverified.

The first device-rate candidate, `7234c845`, is retained as a [failed application run](../../research/publication/windows-portability/application-run-40044766254/observation.json) and [failed component run](../../research/publication/windows-portability/run-40044766174/observation.json). Its SoXR build and probe succeeded, but the validator rejected a successful compiler command's empty log. The application passed 268 host controls before stopping; no window checks, PNGs or ZIP were produced. The correction permits empty logs from successful commands while retaining bounded log reads, exit-code checks and pinned source, artifact and build-profile validation. Probe output must still parse and match its recorded result. Both original failures remain unchanged.

The eight Mac CPR audition modes now use shared preparation, contributor proof and output stages. The Windows helper exposes preparation-only inspection and mode-bound export/playback manifests; each seek or resume requests a freshly verified suffix. Stop discards that suffix before returning to source zero. Long sparse timelines still require streaming: the Mac timeline admits up to 24 hours, while the Windows snapshot transport remains bounded to 32 million output frames. Device conversion does not resolve that gap.

Local validation of this integration passed 425 production-helper checks over 48 full/seek/EOF/rewind scenarios, alongside the unchanged 169-check helper gate. The normal macOS application suite passed 279 executed tests, with 118 explicit private-fixture/generator skips. These authored controls are implementation evidence. The subsequent accepted Windows and cross-platform run is recorded below.

## Parallel development gate

The current unaccepted streaming implementation replaces source-mode live WAV snapshots with a separate shared worker, bounded binary records and bounded native source/endpoint queues. Ordinary-project playback and WAV exports retain their snapshot limits. Authored long-timeline controls cover sparse, overlap and near-24-hour cases; the overlap proof retains fully covered contributors. Local worker, host and native tests exercise the new path, but acceptance still requires the exact Windows package, actual window records, cross-platform comparisons and publication review. The existing preview.8 evidence above remains the released baseline until those gates pass. These scheduling and device policies are authored application behavior; they are not observations of a proprietary scheduler.

The [first streaming CI candidate and corrections](../../research/publication/windows-portability/source-stream-ci-correction-20261026/README.md) retain the failed native long-drain and shared ancestor-path observations. The [second streaming CI observation](../../research/publication/windows-portability/source-stream-harness-correction-20261026/README.md) passed all four shared Swift lanes and their 853-check/85-scenario worker suites. The next ordinary workflow gap is creating a new project and importing audio on Windows. The next native compatibility milestone is project-wide CPR composition on both hosts: current source modes audition a selected event or track, and neither host's ordinary project transport composes retained native events. Project composition requires explicit root membership, routing, accumulation and clock evidence; existing default mixer values and diagnostic source modes do not establish those semantics.

The accepted automation editor exposes the shared volume/pan lane model with revision-bound point edits, Read controls, unchanged-edit preservation and undo/redo. Changes to shared semantics must run the macOS and Windows conformance lanes. Record exact toolchain, architecture, configuration, test counts and observed output. Keep static reference evidence, independent numerical controls, reconstructed application behavior, and hardware observations distinct. Preserve original research seals and private fixture boundaries.

Do not declare parity from a successful component build. Reviewed raw CPR import now has bounded native-window evidence. The next compatibility integrations are streaming source timelines, interactive device-rate playback verification, interchange, inline automation and writing workflows. ### Reviewed CPR import

The shared parser, recovery profiles, historical report replay and `CPRProject.importProject` now compile portably. The importer uses exclusive staging and the existing Windows-aware `ProjectFileIO` publication helpers; it verifies the staged model and exact original/report bytes before publishing without replacement. [Local authored controls](../../research/publication/windows-portability/cpr-import-local-20261023/observation.json) passed through both the portable and native macOS core targets. The subsequent [native cross-platform run](../../research/publication/windows-portability/run-39951105337/observation.json) executed the six Windows and seven macOS importer cases in both configurations without failures. These cover the tested publication paths; broader Windows junction/reparse and interactive dialog behavior remain open.

The Windows implementation exposes inspect → review → explicitly accepted partial import through the shared session and a native review window. Preview.3 passes that authored native journey, including cancellation, changed-source rejection, dirty protection, destination cancellation, preserved source and historical report. The [local record](../../research/publication/windows-portability/cpr-review-local-20261024/sequence.json) and separate failed native observations retain the earlier results.

Review confirmation is bound to the source path/name/hash and interpretation profile. Changed input is rejected; the full original and report are preserved in a new destination. Inspection and cancellation leave the active project/history unchanged. Import retains dirty-project protection and switches the session only after validated publication and readback. Historical reports retain their original frozen interpretation.

The helper serializes a bounded review projection with explicit counts and import eligibility: at most 32 items and 128 KiB per page, backed by an import report limited to 8 MiB. The native fixture exercises 15 items on one page; shared and host controls cover pagination and bounds separately. A published-but-unconfirmed import revokes the review and tells the user to inspect the destination before retrying; failed-save confirmation remains required even if a later state reports clean. Broader Windows reparse/containment and interactive dialog behavior remain open. No proprietary executable was used for these authored controls.
